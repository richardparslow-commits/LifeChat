# Medical Lead Capture — Phase 2 (Compliant Design)

**Status:** Draft — **requires Texas insurance counsel and compliance approval before any use.**
**Scope:** Consented medical fact-finding so Richard Parslow (licensed Texas life-insurance broker) can focus on carriers that fit a user's profile.
**Relationship to the request:** The original request contained scripts using prohibited pressure tactics (assumptive closes, scarcity/takeaway, fabricated decline claims). This document implements the same business goal in a compliance-safe form. The pressure tactics are intentionally **not** implemented and are listed in §5 as prohibited.

---

## 1. When this flow runs

- **Phase 2 only**, gated behind the medical capture feature flag and `healthDataCollectionDisabled=false`.
- **Only after** the user opts into the optional medical review.
- **Only with** explicit, current, versioned medical consent (`medical_consent_affirmed=true` + a current `medical_consent_version`).
- Never in the default educational flow (system prompt §7 forbids these fields without consent).

## 2.1 Canonical condition crosswalk (implemented)

Stated conditions arrive as free text ("sugar diabetes", "high BP"), which cannot be matched or queried. `src/medical/condition-crosswalk.ts` maps them onto a small, versioned vocabulary — one ICD-10-CM code, canonical name, and body system per condition — so a profile is grouped the same way every time.

Rules the code enforces:

| Rule                        | Behavior                                                                                                                                                                                                                                                                  |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Consent gate first          | `mapConsentedMedicalConditions()` is the only production entry point and returns `null` unless the flow is enabled **and** medical consent is affirmed **and** versioned. It is not a side door around `HEALTH_DATA_COLLECTION_DISABLED` or the chat gates.               |
| Never guess                 | Matching is exact against a curated alias index after light normalization. No fuzzy/substring matching, no inferred codes. Unmatched text is returned in `unmapped` and left in the user's own words — "complete" means every condition is matched or explicitly flagged. |
| Additive, not destructive   | `medical_conditions` stays verbatim on the record; canonical refs are stored **alongside** it as `canonical_conditions`, tagged with the vocabulary id + version so a later mapping change is reproducible for counsel.                                                   |
| Clinical normalization only | A ref classifies what the user reported. It is never an underwriting judgment, eligibility finding, or carrier decision, and is never shown to the user.                                                                                                                  |
| Sensitive by classification | Canonical refs are TDPSA sensitive health data: encrypted operational record only — never analytics, session history, logs, or the chat response.                                                                                                                         |

Vocabulary id `lifechat-condition-v1`, current version **`1.9.0`**, covers the domains the approved topics and the review literature exercise — cardiovascular (including acute events, arrhythmia, and venous thromboembolism), metabolic/endocrine, autoimmune/inflammatory, neurodegenerative, neurological (including transient ischemic attack, neuropathy, traumatic brain injury), respiratory, sleep, renal, musculoskeletal, gastrointestinal/hepatic, mental health, oncologic (the major tumor sites), hematologic, and infectious — plus the common-chronic domains outside the literature sweep that a carrier medical-history questionnaire still enumerates: gynecologic/reproductive, urologic, dermatologic, ophthalmologic/otologic, ENT/oral, congenital/developmental, and the residual musculoskeletal, gastrointestinal, hematologic, infectious, oncologic, endocrine, respiratory, and mental-health rows. A test locks the vocabulary to be unambiguous (no alias claimed by two codes, unique ICD-10-CM codes) so an ambiguous entry fails the build instead of resolving silently.

**Any** change to a code, canonical name, body system, **or alias** is a version bump with a `CONDITION_VOCABULARY_CHANGELOG` entry in `src/medical/condition-crosswalk.ts`. That array is the source of truth for the table below and for the added codes, and it is asserted directly by the test suite. An alias move is recorded with the same weight as a code change, because a record mapped under the older version resolved the same stated text to a different code — the entry is what makes that record explainable later.

Three tests keep this table honest: every added code must exist in the vocabulary, every moved alias must actually resolve to its new code and no longer to the old one, and each release's condition count must equal the previous count plus what it added — so the vocabulary cannot be edited without recording the release.

**Coverage is a two-way invariant, not a size target.** The vocabulary is "complete" in the only sense that survives review: every canonical alias is classified as health data by the gate (or is a documented `GATE_EXCLUDED_TERMS` entry), **and** every term the gate watches for either resolves to a canonical entry or appears on the documented list of descriptive terms (body systems, measurements, symptoms, pathoanatomic categories) that are not reportable conditions. Adding a condition term to the gate without a crosswalk entry fails the build, and vice versa — so "what is still unmapped" is answerable from the test output rather than from memory.

**"Complete" is declared, not implied.** Since 1.2.0 the claim has a named scope rather than an open-ended promise: `CAPTURE_SCOPE` in `tests/medical-condition-gate.test.ts` lists the common chronic conditions a carrier medical-history questionnaire enumerates, grouped by domain, each paired with the code it must resolve to. Each declared scope is asserted as behaviour in both directions — every phrase must reach exactly its declared code and classify as health data, and each scope's code list must equal its release's changelog entry, so the declared scopes, the release notes, and the live vocabulary cannot drift apart. Everything in the vocabulary that is _not_ in the scope must be source-derived (1.0.0/1.1.0), and every scope code must exist in the vocabulary.

Deliberately outside the **vocabulary**, with reasons: acute and self-limited infections (urinary tract infection, mononucleosis), injuries and fractures, symptom phrases (brain fog, fatigue), procedure states (hysterectomy), functional and cover-definition rows (blindness, loss of speech, terminal illness), and anything whose code would have to be guessed — the carrier covered-condition lists (1.6.0) are made almost entirely of those rows. Since 1.4.0 those same rows are still **gated** — a disclosure of them is classified as health data — but they carry no canonical code, because the vocabulary's contract is diagnosed conditions and inventing a code the person did not state would break the "never guess" rule. Out-of-scope text is never coerced — it is returned in `unmapped` in the person's own words, which is what makes the boundary reviewable rather than invisible.

**The residual gap is measured, not asserted (1.3.0).** A second declared scope, `RESIDUAL_SCOPE`, records the rows two boundary probes found were **neither gated nor mapped** — a disclosure of those travelled to the model untouched and could not be matched afterwards. It is enforced by the same ledger as `CAPTURE_SCOPE` (each phrase resolves to its declared code and is gated; each scope equals its release's `added` list; nothing in the vocabulary sits outside a declared scope unless source-derived). The probe terms themselves are kept verbatim in `BOUNDARY_PROBE_TERMS`, with an assertion that **nothing a probe surfaced is left ungated**: a row may be gated without a code (acute infections, injuries, symptoms, dental and cosmetic findings — each listed on `DESCRIPTIVE_GATE_TERMS` with its reason), but silence is not an allowed outcome. Latest measurement: 64 probe rows, 40 mapped and gated, 24 gated-but-uncoded by policy, 0 silent pass-throughs.

**The third gap is measured the same way (1.4.0).** `PROBE_GAP_SCOPE` records the named diagnoses a 237-phrase carrier-questionnaire sweep (2026-09-19) found were **neither gated nor mapped**, added in six batches of five; the sweep's procedure states, acute infections, and symptoms became documented descriptive gate terms instead of invented codes. `BOUNDARY_PROBE_TERMS` carries the sweep's rows verbatim, with the same closure assertion. Latest measurement: **237 candidates, 55 neither gated nor mapped, all 55 closed** — 28 became new canonical conditions (among 30 codes added), 3 became aliases on existing rows, and 24 became descriptive gate terms (procedure states, acute infections, symptoms, and HPV). The last row, `piles`, closed in **1.5.0** rather than by deferral: it is now an alias on the hemorrhoids entry (K64.9) and is gated by a context rule, because its collision is syntactic — the ordinary sense is the quantifier and phrasal-verb shape ("piles of paperwork", "the work piles up", "he piles on the pressure"), which the rule excludes with a negative lookahead, while a disclosure ("I have piles"), a clinical qualifier ("bleeding piles"), or a possessive ("my piles") supplies the medical reading. The boundary ledger has no deferred rows left, and a test asserts that.

**Every condition a release adds now carries a phenome cross-check mark.** The vocabulary and the PTSD phenome map (`src/phenome/ptsd-phenome-map.json`, built from the three reviewed syntheses under `docs/phenome-mapping-rules.md`) answer different questions, and `src/phenome/sequelae-crosswalk.ts` keeps them from being read as each other: each condition added to `lifechat-condition-v1` is marked `graded_row` (the map carries a row, and the entry repeats that row's tier), `d_no_studies` (a plausible sequela no source measured — R43's explicit finding, never "no association"), or `not_a_sequela` (present at birth, chromosomal, or hereditary with childhood onset). The cross-check of the 30 conditions **1.4.0** added is deliberately unflattering: **one** (paroxysmal supraventricular tachycardia) is covered by any row, and that row is tier `D` — mechanism-only — because reduced heart-rate variability is asserted with no epidemiology. Twenty-three are study gaps; six are exclusions; and nine could not be placed in a domain at all, because the phenome map's §12 sweep has no dermatologic, lymphatic, urologic/genital, ophthalmologic, or congenital domain — a gap the crosswalk records in words rather than hiding. Forcing that cross-check is what surfaced the map's own missing domain rows: renal, neurological, respiratory, gastrointestinal/hepatobiliary, and oncologic outcomes had no row, so they were added as explicit `D` rows, alongside the two rows the reviewed literature already supported (severe infection at tier B, and the mandatory `trauma`-stratum functional-somatic row).

**The fourth gap was found by a different _kind_ of source (1.6.0).** The three sweeps above all measured the same register — what a person, or a questionnaire, says about their history. A carrier's critical-illness covered-condition lists are different: they enumerate what a _claim_ is triggered by, so they name the catastrophic end of the spectrum an underwriter asks about (coma, paralysis, organ transplant, terminal illness, loss of sight or speech) and the conditions a payout hinges on. `CRITICAL_ILLNESS_SCOPE` records the ten named diagnoses a 51-phrase sweep of those lists found were **neither gated nor mapped**, added in two batches of five. The rows the lists also carry that are not diagnoses — procedures (bypass, valve surgery, transplant), injuries (burns, head trauma), and functional or cover-definition rows (blindness, loss of sight, loss of speech, paralysis, terminal illness, loss of independent existence) — became documented descriptive gate terms instead, which is why the corpus measures 23 mapped-and-gated and 28 gated-but-uncoded, with **0 silent**. Three aliases landed on existing rows rather than new codes: the two spellings of pulmonary hypertension, and `loss of hearing`, which the vocabulary already carried as hearing loss (H91.90) — the list simply named the same condition differently (and, since the questionnaire corpus spells it the same way, it moved that corpus's single row too: 184 mapped-and-gated, 53 descriptive).

**The fifth gap came from a code book (1.7.0).** Every source so far had been prose a human wrote _about_ a person — a questionnaire, a covered-condition list. The next one is a classification structure: the three-character category titles of WHO ICD-10 Chapter IX, 77 rows written to organize codes rather than to describe anyone. Measuring it asked a harder question than the earlier sweeps did — not "does the gate see this sentence?" but "when a person states the thing the code book names, does either system see it?" — and the answer found three kinds of hole. Two were spelling: the vocabulary carried `hemorrhage` and `hemorrhoids` but not the British `haemorrhage`/`haemorrhoids`, so a British visitor's haemorrhagic stroke and haemorrhoids were both **silent**. One was a synonym: `stroke` was mapped, `cerebral infarction` was not. Three were conditions nobody had named yet (phlebitis, nonspecific lymphadenitis, atrioventricular block). The remaining category constructs — "other diseases of pericardium", "other disorders of arteries and arterioles", "other disorders of veins", "diseases of capillaries", "other and unspecified disorders of circulatory system" — are not diagnoses anyone states, so they are now gated by a narrow clinical term (`pericardium`, `arteriole`, `veins`, `capillaries`, `circulatory`) rather than given an invented code. One of those terms carries a stated cost: `veins` is word-matched in the plural only, so "in the same vein" stays clear while the metaphor "the veins of the market" is gated — the fail-safe direction, recorded rather than hidden.

**The sixth measurement came from the same code book, one chapter across (1.9.0).** The Chapter IX sweep asked whether the vocabulary sees what a code book names; the obvious next source was the chapter the stone family itself sits in — N00–N99, diseases of the genitourinary system — whose 85 category titles are almost all _constructs_ rather than diagnoses ("other disorders of bladder", "other noninflammatory disorders of the vagina"). That is why this sweep's shape is different from every earlier one: 41 rows were silent, but only thirty of them name a diagnosis a person could state. Those thirty are canonical rows in six batches of five, each title verified against ICD-10-CM before use. The constructs close as documented descriptive gate terms, and the sweep found two genuine codebook holes worth recording: `urethral stricture` has no sex-free billable code since FY2026 split N35.9 into N35.91 (male) and N35.92 (female), and the corpus row `benign mammary dysplasia` needed the site-free member N60.99 rather than the N60.9 header, the same way `unspecified lump in breast` needed N63.0 — the lump rule's own row, finally matchable. One alias moved: an unqualified `kidney failure` is the unspecified row (N19), not end-stage renal disease. The corpus therefore measures **85 candidates, 28 mapped and gated, 57 gated-but-uncoded by policy, 0 silent** — the largest gated-not-coded share of any source, which is the honest signature of a classification structure rather than a description of a person.

**Re-running the measurement (the sweep tool).** The numbers above come from a measurement, so the measurement is a committed tool: `npm run conditions:sweep` runs a candidate list through both systems and reports every row as mapped-and-gated, mapped-but-ungated, gated-but-uncoded, classified-otherwise, or **silent** — the last being the class the sweeps exist to find. It exits non-zero on silent or mapped-but-ungated rows, so a corpus can gate CI the way the verdict and persona gates do. **Four** corpora are committed and swept by default: `docs/medical-condition-candidate-phrases.txt` (the 237 phrases the questionnaire sweep was measured against), `docs/medical-condition-candidates-critical-illness.txt` (the 51 phrases the carrier covered-condition lists yielded), `docs/medical-condition-candidates-icd10-chapter-ix.txt` (the 77 three-character category titles of ICD-10 Chapter IX) and `docs/medical-condition-candidates-icd10-chapter-xiv.txt` (the 85 category titles of ICD-10-CM Chapter XIV, the chapter the stone family sits in) — all written down before any of their rows were mapped. Replacing any of them, or passing one or more paths, is how the next source is measured:

```bash
npm run conditions:sweep                        # all four committed corpora
npm run conditions:sweep -- --all               # every row, not only the problems
npm run conditions:sweep -- my-questionnaire.txt
npm run conditions:sweep -- --json
```

A candidate list is one phrase per line with `#` comments ignored, or a JSON array of strings. Current measurement: the questionnaire corpus **237 candidates, 184 mapped and gated, 53 gated-but-uncoded by policy, 0 mapped-but-ungated, 0 silent**; the critical-illness corpus **51 candidates, 23 mapped and gated, 28 gated-but-uncoded by policy, 0 mapped-but-ungated, 0 silent**; the ICD-10 Chapter IX corpus **77 candidates, 14 mapped and gated, 63 gated-but-uncoded by policy, 0 mapped-but-ungated, 0 silent**; the ICD-10 Chapter XIV corpus **85 candidates, 28 mapped and gated, 57 gated-but-uncoded by policy, 0 mapped-but-ungated, 0 silent**. Tests re-run all four sweeps on every build, so these sentences cannot drift from the code the way a remembered number can.

**The deterministic gate carries the same vocabulary.** `detectSensitiveData()` in `src/security/security-controls.ts` holds the condition vocabulary itself — `HEALTH_CONDITION_TERMS` (substring stems, for prefixed compounds like hypothyroidism and osteoarthritis) and `HEALTH_CONDITION_WORD_TERMS` (whole-word tokens such as `hiv`, `copd`, `a-fib`) — so a condition named plainly ("I have lupus", "I wear a CPAP for sleep apnea") is classified as health data without any disclosure word like "diagnosed". Gating is never narrower than the vocabulary the broker matches against: a test asserts every synonym is either gated or on `GATE_EXCLUDED_TERMS`, the documented list of abbreviations (`ms`, `ra`, `mi`, …), ambiguous symptom words (`panic`), and the lay synonyms `piles`, `stones` and `lump` that collide with ordinary English. Seven of those entries — the abbreviations `MS`, `SLE`, `TIA`, `TB` and the lay words `piles`, `stones` and `lump` — are excluded only as _bare_ tokens and are gated by context instead, through the declarative registry in `src/security/context-qualified-terms.ts` (one object per term; `hasContextQualifiedTerm()` evaluates the patterns derived from it): a disclosure word next to the token ("I have MS", "I've got MS", "I suffer from MS", "I tested positive for TB", "I was hospitalised for SLE", "do I need to declare MS?"), a clinical word after it ("MS diagnosis", "SLE flares", "TB carrier", "MS-related fatigue", "TIA survivor"), family framing ("MS runs in my family"), or the possessive form ("my TB is latent"). `TIA`, `TB` and `SLE` also match their dotted spellings ("T.I.A.", "T.B.", "S.L.E."). `piles` uses the same adjacency rule plus two of its own — a clinical qualifier ("bleeding piles", "internal piles") and a possessive ("my piles", "his piles") — and never matches immediately before `of`, `up`, `on`, `in`, `into`, `onto` or `upon`, which is the shape every ordinary use has ("piles of paperwork", "we have piles of data", "the work piles up"). The question path treats it the same way: "Is piles curable?" is a health topic question, while "Are piles of paperwork a problem?" stays silent. Because those shapes are derived from each entry rather than written per term, a declared guard cannot be forgotten on one path: `tests/context-qualified-terms.test.ts` asserts structurally that it appears in every pattern that watches the token, and proves with a synthetic entry — run through the same production functions — that the next lay synonym needs nothing but its data.

**The next lay word was chosen by measuring six candidates (`lump`).** `lump` is the word a breast history is almost always stated with ("I found a lump in my breast"), and it was completely silent: the vocabulary carries no `lump`, and no generic pattern sees the discovery verbs. Six candidates were graded in both directions against realistic messages — `lump`, `rash`, `mole`, `cold`, `bug`, `fit` — and `lump` was the only one with **zero** ordinary false positives across twelve product-realistic sentences, because its worst collision is the product's own vocabulary: `lump sum` is how the payout is discussed, so a bare token would have handed off "should I take the lump sum or monthly payments?". The others were deferred with their measured reason: `fit` ("I want to get fit" gates on the shared `get`), `mole` ("we have moles in the garden" gates on the shared `have`), `rash` ("Is it rash to switch policies?" is falsely named on the question path), `cold` (its guard would be an open list of noun senses), and `bug` (half its medical phrasings need a verb the shared lists do not carry). `lump`'s guard is a lookahead for the payout compound, the quantifier and the phrasal verb — "a lump of coal", "I'll have to lump it", "lump them together" — so no possessive or disclosure word can resurrect them, and its question path is clean in both directions: "Is a lump in the breast serious?" is a health-topic question, "Is the lump sum taxable?" is nothing.

**A term can declare its own adjacency vocabulary — the constraint the lump measurement forced.** The registry's two adjacency word lists were shared by every entry because they describe how a person states a diagnosis. The lump corpus showed the boundary: "I found a lump" is how a lump is stated, but adding `found` to the shared list would have made "I found stones for the patio" gate — the stones entry accepting a disclosure its corpus never measured. So an entry may declare `disclosureWords` / `clinicalWords` of its own (active voice "I found a lump", "I noticed a lump", "there's a lump"; passive "the lump was found on the scan", "the lump was removed in 2022", "lump biopsy results"), appended to the shared lists **for that entry alone**. `tests/context-qualified-terms.test.ts` asserts structurally that each declared word appears in its own entry's pattern and in no other entry's, and the stones collision corpus now carries "I found stones for the patio" as the boundary that fails if the words are ever shared.

The rule is measured, not asserted. `tests/gate-road-test.test.ts` sweeps 36 disclosure templates across all four tokens plus a curated corpus of realistic messages, and requires **every** combination to gate; a companion benign sweep requires the collision sentences to stay silent. The lay words `piles` and `lump` each carry a two-directional corpus of their own, and the stones/lump boundary is pinned in both: "I found a lump" gates, "I found stones for the patio" does not. Its first pass found seven live leaks in ordinary phrasings ("I've got MS", "I suffer from MS", "MS sufferer here", "MS runs in my family", "I tested positive for TB", "latent TB", "I'm a TIA survivor", "MS fatigue") and a 92/104 template score, all of which are now closed.
**A registry entry without a collision case fails CI.** `REGISTRY_COLLISION_CORPUS` in the same file maps every live `CONTEXT_QUALIFIED_TERMS` id to the benign rows that prove its guard, and the contract suite at the end of the file requires each entry to have at least one of them — plus a reviewed depth floor of three, the smallest corpus in the registry today — with each row in a corpus the classification tests actually iterate — so a term cannot be added to the registry without its ordinary counterpart, and the reverse direction is checked too (a stale ledger key, or a corpus pointing at phrases no test runs, fails). The check is demonstrated rather than assumed: adding an eighth entry to the registry turns the build red with that entry's id in the diff. This is the corpus-side counterpart of the structural assertion in `tests/context-qualified-terms.test.ts`, which proves what the generated patterns watch; between them, the derived machinery and the measured collision surface each fail loudly. `npm test` is the CI job (`.github/workflows/ci.yml`), so the contract runs on every push. The evidence for the missing collision belongs in the corpus, not in a reviewer's memory — the `tb` entry, the one term that had no ordinary rows at all, now carries the terabyte frames ("the drive holds 2 TB") while the shape it cannot separate, "I have 2 TB of photos", is pinned in `TRADEOFFS` as an accepted false positive in the safe direction.

**The syntactic-collision class, measured in both directions.** The class `piles` opened is a lay synonym or phrase whose ordinary sense is a _frame_ rather than a second meaning of the word: the quantifier ("piles of paperwork"), the place ("the stones in the driveway"), the task ("stones to move"), the mass noun ("growth of the market", "stone is cheaper than brick"), the "<word> of" metaphor ("discharge of the mortgage"), the transitive verb ("they passed out the forms"). Five candidates were probed, each with a medical corpus and an ordinary counterpart (`SYNTACTIC_COLLISION_CASES`, 52 medical phrasings and 63 ordinary ones):

| Candidate   | Closed as                                                                                                                                       | Residue                                                                                                                                           |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `stones`    | registry entry — 13 medical phrasings gate, including "I have stones", "stones in my urine", "bladder stones", "gall stone", "I passed a stone" | none; 16 ordinary frames stay silent ("stones of the garden path", "the stones in the driveway", "stones to move", "a driveway with stones")      |
| `growth`    | pattern family, determiner-based — 12 medical phrasings                                                                                         | "a growth of 5 cm" stays open: the "of" shape is also how a chart is read ("a growth of 5%")                                                      |
| `discharge` | pattern family — 13 medical phrasings                                                                                                           | none; 13 ordinary senses stay silent ("discharge of the mortgage", "discharged from the army", "the discharge date on the loan")                  |
| `passing`   | phrase family — 10 medical phrasings, including "passed out", "passing blood", "blood in my urine"                                              | "my father passed away last year" stays open: bereavement, not the visitor's own health datum                                                     |
| `pads`      | qualified phrases only — 4 medical phrasings                                                                                                    | the bare verb frames ("I wear pads", "I use pads every day") stay open: the same frames are ordinary ("I wear knee pads", "my pads are worn out") |

What the measurement did not support is recorded rather than guessed at: `SYNTACTIC_COLLISION_CASES[].open` asserts each residue is still silent **with its reason**, so a future rule that closes one fails the row until it moves into the medical corpus, and the two accepted false positives ("how many stones do we need" — the plural named in a question containing "we"; "I weigh 12 stone" — the body-measure field) are pinned in `TRADEOFFS`. The `stones` measurement is also what gave the registry its second guard position and its named-spelling control: its ordinary shapes include words that _follow_ the token ("stones of", "in the") and one that _precedes_ it ("with stones"), and the singular is a mass noun, so only the plural is watched on the question path — "Are stones painful?" is a health topic question, "is stone cheaper than brick?" is nothing.

One residue was a mapping rather than a gate, and **1.8.0** closed it. The newly gated anatomical phrases are real diagnoses with standard codes, so `STONE_FAMILY_SCOPE` records "bladder stones" (N21.0, calculus in bladder) and "ureteral stones" (N20.1, calculus of ureter) as canonical rows, and the two-word `gall stone` the same sweep measured joined the K80.20 aliases — the 1.4.0 corpus carried only the one-word "gallstones", so the spaced spelling gated without being matchable. It is a mapping-only release: the gate had already classified every phrase, which is why the sweep's bucket counts are unchanged and the closure is asserted in the scope ledger rather than measured as a silent row closing.

Three ambiguity guards keep the collision surface from growing, each stripping the non-clinical sense from a copy of the text, case-sensitively, before matching: `Ms.` (the honorific, so "MS" survives), `Tia` (the name, so "TIA"/"tia" survive), and `M.S.` before a degree word ("an M.S. in economics"). The cost of each guard is stated where it lives and asserted in the corpus: a sentence-initial "Tia" meaning the stroke, and the degree sense after a possessive or copula ("my M.S. is in economics"), are **not** gated. Both fail in the safe direction — an extra handoff, never a silent pass-through.

**The context rules are proven at the endpoint, not only in the classifier.** A gate test shows what `detectSensitiveData()` returns; it does not show what the application _does_ with the answer. `tests/api-endpoints.test.ts` therefore drives the `piles` corpus — “I have piles” and “piles of paperwork” among six disclosure forms and six ordinary senses — through `POST /api/chat` with a freshly loaded app per request, and asserts the endpoints of the behaviour rather than the classification alone: a disclosure returns `state: "handoff"` with risk flag `sensitive_data_disclosed` and `handoff_reason: "health_data_disclosed"`, its copy names the licensed broker, and its text is stored **only as the redacted placeholder** — the same history `getHistory()` hands the orchestrator on the next turn, so a later turn cannot put the condition in front of the model. A collision sets none of those markers, reaches the orchestrator instead of the refusal, and is stored **verbatim**, which is what “untouched pass-through” means in a test rather than a sentence.

**"Condition" is only a health word in context.** The disclosure list watched the bare word, so it matched any sentence containing it — "what conditions apply to my application?", "what are the terms and conditions?", "conditions of sale apply", "market conditions are rough" were all classified as health data and handed off. The word is genuinely two words: a medical state someone has, and a requirement attached to a product. `CONDITION_PATTERNS` now requires the context that separates them — it counts when the condition **belongs to someone** ("my condition", "my father's condition"), **points at one** ("a condition", "the condition" — singular only, since "the conditions of the policy" is contractual), is **health-qualified** ("a chronic condition", "pre-existing conditions", "a skin condition"), or **names examples** ("conditions such as asthma"). Deliberately not counted, each because it is idiomatic in the contractual sense: `any` ("are there any conditions on the payout?"), `other` ("other conditions apply"), and the bare plural. First-person plurals with no qualifier ("I have other conditions", "I have conditions that are managed") are covered by a separate clause, because a bare plural would otherwise fall through and that is a real disclosure phrasing — requirements attached to a product are not something a person _has_ about themselves. Both directions are asserted in `tests/gate-road-test.test.ts` — 8 contractual sentences silent, 10 guarded medical forms gated — and a possessive-noun case caught a real bug while writing them (`\w['’]s` only ever matched a one-letter possessor; it needed `\w+`).

**The rest of the meta words, same treatment ("treatment", "heart", "symptom", "prescription", "disease", "disorder").** Each also matched bare, and each collides somewhere in this domain: `treatment` ("what is the tax treatment of the proceeds?", "the treatment of the claim", "equal treatment for all applicants"), `heart` ("at the heart of the matter", "the heart of the policy"), `symptom` ("a symptom of a slow claims process"), `prescription` ("the prescription of rates"), `disease` ("the disease of rising premiums"), `disorder` ("the disorder of the ledger"). They did not all need the same rule, and finding that out by testing rather than by design is the interesting part:

| Word                                                      | Rule                                                               | Why that rule                                                                                                              |
| --------------------------------------------------------- | ------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| `condition`                                               | positive — owner, health qualifier, example framing                | its ordinary sense ("terms and conditions") has no distinguishing suffix                                                   |
| `treatment`                                               | positive — owner, health qualifier, clinical anchor, clinical verb | its ordinary sense is the _preceding_ word ("tax", "equal") or "treatment of the claim"                                    |
| `heart`, `symptom`, `prescription`, `disease`, `disorder` | negative — excluded only in the "<word> of <something>" metaphor   | every other use is medical, including the names of conditions that **end** in the word                                     |
| `diagnosis`                                               | positive — person, clinician, clinical anchor, temporal marker     | its ordinary sense is the _mechanism_ sense ("diagnosed the issue"), which shares no subject with a person's own diagnosis |
| `therapy`                                                 | negative — two word prefixes (`retail`, `aroma`) excluded          | every other use is a treatment, including the compounds (chemotherapy, physiotherapy)                                      |
| `medication`                                              | none — left broad on purpose                                       | no ordinary sense measured at all                                                                                          |

The negative rule exists because the first version — positive qualification, the same shape as `condition` — silently dropped named conditions: `peripheral artery disease`, `reactive airway disease`, `chronic obstructive pulmonary disease`, `post-traumatic stress disorder` and `panic disorder` all stopped being classified as health data, because nothing in those names is a "qualifier" the rule could have listed. The existing parity tests caught every one of them, which is what those tests are for. Two medical "of" shapes are opt-in exceptions ("symptoms of my condition", "a disease of the liver"), and `heart` deliberately does not take them, because for `heart` that shape _is_ the metaphor ("the heart of my plan"). `heartburn` is its own entry: it is the vocabulary's synonym for GERD, and `\bheart\b` never matched it.

**The seven are one registry now, not seven regex families.** `src/security/context-family-terms.ts` declares each word as a single object — its spellings, its rule shape, and the ordinary sense written down — and every pattern is generated from that data, the same move `context-qualified-terms.ts` made for the excluded tokens. A `context-required` entry lists its clauses in the order they were measured (`owner`, `disclosure`, `possessor`, `definite-article`, `qualifier`, `anchor`, `verb`, `example`), each carrying the words or introducers it counts; an `of-metaphor-excluded` entry declares `medicalOf` explicitly, which is why `heart` cannot inherit the medical "of" clauses the other four take. What used to exist only as an inline regex is now data a test can read: `condition`'s singular-only `the` clause names the spelling it watches, `treatment`'s owner clause carries `excludeOf: true` inside the generated pattern — so a clause cannot be added without the lookahead that makes "the treatment of the claim" ordinary — and `heartburn` is listed with the reason it belongs to the heart family. `tests/context-family-terms.test.ts` asserts the structure (every pattern watches the spellings it was declared for, each rule carries only the data it reads, a definite-article clause may only name a declared spelling) and proves the machinery is data-driven with synthetic entries run through the production builder. The refactor is behaviour-neutral: a 52-sentence snapshot spanning all seven families plus growth, discharge, passing, pads, diagnosis, therapy and the body-measure fields — every family that shares the builders — is byte-identical before and after.
**The three words the first pass narrowed by hand are registry entries now — the clause vocabulary grew to express them.** `diagnosis`, `therapy`, `therapist` and `medication` were hand-written patterns in `security-controls.ts`; they are entries in the same registry, in the same clause order as the patterns they replaced, so the two can be read side by side. Diagnosis needed four clause kinds the first seven words never used — `person` ("I was diagnosed last year", "was I diagnosed?"), `clinician` ("the doctor's diagnosis"), `temporal` ("recently diagnosed", "diagnosed last year") and `relative` (family history, either word order) — plus three entry controls that keep a clause exactly as wide as the measurement was: `stem` (the word is `diagnos` + `\w*`, because the old stem's reach was the point), `spellingGroups` + a clause's `form` (three clauses count the noun and not the verb: "diagnosis date" is medical, "diagnosed date" is not — and "diagnosed but untreated" is limited to the past participle, because "diagnosis and treatment" is a phrase about care in general), and `intervening` (an owner clause may take only the listed adjectives into its gap: "my recent diagnosis" without opening "my mechanic diagnosed"). `therapy` and `therapist` declare the rule shape the bare stems always had — `bare`, with the two word-initial prefixes as declared `prefixExclusions`, each recording whether it is written joined to the word or separated by a space (the difference between `(?<!aroma)` and `(?<!retail\s)` is the whole exclusion) and with `compounds` recording why the leading `\b` is off: `chemotherapy`, `physiotherapy` and `psychotherapy` must keep matching. `medication` is `bare` with no controls at all, which is the measurement written down: no ordinary sense was found ("medicate the problem" and "medicated shampoo" do not contain the word), so the plural and the informal form `meds` are declared spellings rather than left to a stem.
**The migration was proved neutral clause by clause, before the old patterns were deleted.** A 131-sentence corpus — every documented medical and benign form for the three words plus the mechanism senses, the prefix collisions, the compounds, `self-medication`, `diagnosed in 3rd grade` — was run against the hand-written family and then against the registry's generated patterns with the old ones still in place: which clause matched, sentence by sentence, was identical (0 differences), so deletion could only remove duplication, not behaviour. The same corpus was re-run through `detectSensitiveData` after the deletion: 95 gated, 36 silent, byte-identical to before. The comparison earned its keep twice. It caught a real regression in the first draft — the aromatherapy carve-out had been compiled as `(?<!aroma\s)` instead of `(?<!aroma)`, which un-excluded three benign sentences on the spot — and it caught two clauses that had quietly widened: the connector form (`diagnosis and treatment` would have started gating) and the interrogative verb list, which had absorbed the informal `got|get|gets` that were only ever measured in the declarative order. A third control, `possessive` on the clinician clause, was removed rather than asserted: the 10-character window already covers "the doctor**'s** diagnosis", so the flag changed nothing — data pretending to be a rule, which is the failure the registry's own invariants exist to catch.

Two accepted false positives remain, both in the safe direction: the rhetorical "is there a prescription for a good policy?" and "a disorder in the claims queue" gate, because "a prescription for my medication" and "a disorder in my records" are the same shapes and the medical reading has to win.

**The last three were decided by measuring their metaphors, not by asserting they were rare.** `diagnosed`, `medication` and `therapy` had been left broad on the reasoning that their metaphors are rarer than the medical use. That reasoning had never been checked, so it was checked: 43 probe sentences per direction, graded before any change. It held for one word and failed for two.

| Word         | Probe before | Probe after               | What the measurement found                                                                                                                                                                                                                                                                                    |
| ------------ | ------------ | ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `diagnosis`  | 12/20        | 20/20                     | Seven ordinary sentences false-gated — "the problem was diagnosed as a timing issue", "my mechanic diagnosed a faulty sensor", "can you run a diagnosis on my account?" — and one **disclosure** was missed outright: `diagnos(?:ed\|is)` never matched the plural noun, so "I have two diagnoses" was silent |
| `therapy`    | 8/18         | 18/18 (4 accepted, below) | Eight ordinary sentences false-gated, six of them one of two word-PREFIX collisions: `retail therapy` (the idiom, and a business name) and `aromatherapy` (a product and a business)                                                                                                                          |
| `medication` | 5/5          | 5/5                       | No ordinary sense exists. The only candidates, "medicate the problem" and "medicated shampoo", do not even contain the stem — so it is left broad because the measurement said to, not because nobody looked                                                                                                  |

`diagnosis` took the same positive rule as `treatment` — a person, a clinician, a clinical anchor or a temporal marker — rather than a list of non-medical objects, because objects are unbounded ("the issue", "the fault", "the leak", "the delay", and whatever the next one is). A be/have verb is required when the subject is a pronoun, which is exactly what clears "they diagnosed the leak" (a practitioner diagnosing an object) while keeping "I was diagnosed last year" (a person stating their own diagnosis). `therapy` needed the opposite shape — two negative lookbehinds — because both of its collisions are word prefixes, and `\b`-anchoring the stem would have dropped `chemotherapy`, `physiotherapy` and `psychotherapy` along with them.

Two leaks in the same families surfaced on the way, both fail-unsafe, both now closed: `\bmeds\b` ("I stopped taking my meds", "my meds are expensive", "I am on meds") and `therapist` — which does not contain "therapy" at all, so "I see a therapist twice a week" had been travelling unclassified. `therapist` carries the occupation carve-outs (`massage`, `beauty`, `nail`, `hair`, `spa`), because "I am a massage therapist" answers an occupation question while "physical therapist" is a treatment relationship.

**The narrowing is guarded against its own risk — losing a real disclosure — by measurement rather than by care.** `META_WORD_COVERAGE` in `tests/gate-road-test.test.ts` is a 46-row sweep in which every row states a diagnosis, a treatment relationship or a medication **without naming a condition**, so nothing but that word's own pattern can carry it. Six forms leaked on the first pass — "I received a diagnosis", "I obtained a diagnosis", "I asked for a diagnosis", "they diagnosed me", "diagnosed but untreated", "diagnosis pending" — and each now has a pattern and a row. Accepted false positives are recorded rather than hidden: "wine is my therapy" and "the gym is my therapy" gate ("dialysis is my therapy" is the same shape), as does the joke "I need therapy after this week" and the contrived "the therapy of a long holiday" — nothing measurable justifies excluding the of-shape for this word.

**The lifestyle and body-measure fields got the same probe, and it split them six-to-four.** `height`, `weight`, `tobacco`, `alcohol`, `substance`, `smoker`, `bmi`, `nicotine`, `blood pressure` and `cholesterol` were all one bare substring alternation; graded in both directions, six had measured collisions and four had none.

The probe found something else in the same field, in the fail-unsafe direction: the **verb** was ungated in every form — "I weigh 180 pounds", "she weighs 120 pounds", "I weigh myself every morning", "the nurse weighed me", "I was weighed at the clinic". The old stem watched the noun only, so five direct statements of an underwriting field travelled unclassified. They are carried now, in the numeral, reflexive and clinical shapes only, because "I weigh the options" is the same verb in its figurative sense.

**Coverage was re-measured against the patterns being replaced, not just forward.** All 57 medical rows the old stems caught were graded again under the new rules: **zero lost, seven gained** (the `weigh` family). The durable artifact is the corpus, not the comparison — `HEALTH_FIELD_COVERAGE` is an 86-row sweep in which every row states a body measure, a lifestyle field, a substance or a clinical state without naming a condition, so only that field's own rule can carry it. Two trades are recorded rather than hidden, both failing safe: "I sell tobacco products" gates, because "I **use** tobacco products" is the same noun phrase; and "I bought a smoker for the garden" gates, because a purchase-verb window would also swallow "I bought a policy for my father, a smoker" — a real disclosure with a purchase in it. One residual is stated plainly: a units-only statement with no medical word at all — "I am 5 foot 10" — is invisible to any pattern for `height`.

**The last four words measured the other way round.** `stress`, `illness`, `smoke` and `drink` were flagged in the source comments as collision-prone — words whose ordinary English sense would make a rule noisy. Measured in both directions, the reputation was wrong about nearly all of them: every ordinary sentence was _already silent_ (they were not matched at all), while **26 clinical forms were ungated**. Only one over-match existed anywhere in the set, and it was a product name.

The `illness` carve-out is a lookahead rather than a lookbehind, and that is the whole design: "**I have a critical illness**" is a disclosure and "does it include **critical illness cover**" is not, so only the following word distinguishes them. The list is the sales nouns — cover, insurance, policy, plan, quote. `claim` was tested and deliberately left _in_: "my critical illness claim was refused" and "I filed an illness claim" are statements that imply the condition, and the general question form ("how does a critical illness claim work?") comes out a health **topic** question, which is the right classification for it anyway. Bare "is illness covered?" is likewise a topic question, not a disclosure.

The adjective `ill` needed one extra care that only showed up in testing: a hyphen is a word boundary, so the copula form swallowed "is **ill**-advised" and "am **ill**-prepared". Every `ill` pattern now carries a `(?!-)` lookahead — the hyphen _follows_ the word, so a lookbehind would never see it — and both collisions are asserted as benign.

Two limits are worth stating rather than implying: "I am stressed" and "I feel stressed" are left ungated, because in this domain they are colloquial and the clinical forms (levels, leave, a clinician, a consequence) are what a disclosure looks like; and "I smell smoke" is not caught, since the pattern requires a person as the _subject_ of smoking rather than someone near it.

Each of the twenty words now carries **both** corpora in `tests/gate-road-test.test.ts` — a benign list proving the ordinary sense stays silent and a medical list proving the narrowing cost no real disclosure — plus a structural assertion that no word can be narrowed without both. Writing them caught a silent coverage loss of its own: the first `prescription` pattern was singular, so "my prescriptions are expensive" matched nothing.

**How the endpoint half of the suite is kept honest.** One full-suite run failed a single endpoint assertion — an ordinary sentence classified as a handoff — and passed in every rerun, so the first job was to make that kind of failure diagnosable and its causes impossible rather than to declare it fixed. Four changes:

- **A fresh app per endpoint test.** The `/api/chat` describes used to share one app instance per describe, which means one rate-limit store, one session store, one page-context bridge and one module registry across ~40 requests. Nothing in the gate reads those, but an endpoint test whose outcome depends on how many requests ran before it cannot be trusted to fail for its own reason. `loadApp()` resets the module registry, so `beforeEach` now builds an app whose module state is pristine, and every test does one request against it.
- **One object comparison instead of one field at a time.** The failing test was asserted field by field, so the only evidence a rare failure leaves is a single field name. It now compares `{status, state, risk_flags, assistant_message}` in one `toEqual`, so a recurrence prints the whole response.
- **The violated property, asserted directly.** Classification must be a pure function of the text: the same sentence is classified 200 times in a row and must return the same category every time (the stateful-regex and module-counter class of bug), and the same benign message is sent twelve times through the endpoint — eleven fresh sessions plus one repeat — and must come back identical and never a handoff.
- **Cross-instance agreement.** `loadApp()` resets the module registry, so the app runs a _newer_ instance of the security module than the one the test file imported at the top. The two are now asserted to agree on a sample, because if they ever drifted, every unit assertion in the file would be describing a gate the endpoint does not run.

Stability is then measured, not asserted: six consecutive full-suite runs, a serial run (`--maxWorkers=1`), a high-parallelism run (14 workers) and a deliberately tight per-test timeout (`--testTimeout=400`, against a 5-second default and measured per-test times under 400 ms) all pass 1349 tests. No leaked handles are reported. The observed failure's exact field was never recovered — which is why the assertions now print all of them — and `state: 'handoff'` has exactly two reachable producers, the sensitive-data refusal and the PII-to-state-machine path, neither of which the current patterns can produce for an ordinary sentence.

**A question about a condition is not a disclosure of one.** (Gate change only — the condition vocabulary and its release history are unchanged. No conditions were added, so no changelog entry applies.) Asking "Is TB curable?" handed off the same way as saying "I have MS", and was classed the same way — which misstated the visitor's action: the reply told them not to share diagnoses, the message was redacted as a disclosure, and the record carried `sensitive_data_disclosed`. Whether that happened at all was incidental, depending on whether the vocabulary happened to cover the condition: "What is lupus?" was blocked, "Is TB curable?" and "does MS affect my life insurance rate?" travelled to the model untouched. The classification is now explicit and decided by one rule, `detectHealthTopicQuestion()`: a leading interrogative, a condition reference (crosswalk vocabulary, the common named conditions, or one of the four abbreviations with the guards applied), and **no first-person or family framing**. Three outcomes, not two:

| Input                                                                  | Classification          | Why                                                                                   |
| ---------------------------------------------------------------------- | ----------------------- | ------------------------------------------------------------------------------------- |
| "I have MS", "my SLE is stable", "history of TB"                       | `health_data`           | the visitor's own health                                                              |
| "does MS affect my rate?", "do I have MS?", "does my father have MS?"  | `health_data`           | personal framing makes the question a personal health question — an implied condition |
| "Is TB curable?", "What does TIA stand for?", "How is cancer treated?" | `health_topic_question` | about a topic, about nobody in particular                                             |

The safety property is identical in all three: blocked before the model, deterministic licensed-broker handoff, message kept out of session history so a later turn cannot put the condition in front of the model, and `medical_review` with affirmed consent remains the only surface that accepts it. What differs is the visitor-facing copy (no "don't share diagnoses" for someone who shared nothing), the `handoff_reason` (`health_topic_question`, not `health_data_disclosed`), and the risk flag (`health_topic_question`) — so the compliance record states what actually happened. A trailing question mark alone is not enough ("history of SLE?" stays a disclosure), and the response schema carries the same invariant as the disclosure flag: the topic flag requires `proposed_action=request_human_handoff` or `none`. The split is asserted at the unit level, through `/api/chat`, and in `tests/gate-road-test.test.ts`, where the topic questions previously recorded as undecided judgment calls are now assertions.

## 3. Consent flow (implemented)

1. Assistant proposes the optional medical review after qualification, with a just-in-time notice: which fields, why (carrier matching by the licensed broker), optional nature, withdrawal/deletion route.
2. The application presents `RECOMMENDED_MEDICAL_CONSENT_COPY` as an **explicit, unchecked, opt-in** control. Ambiguous or hedged replies are treated as **not** consented (system prompt §9).
3. Consent is versioned (`medical_consent_version` + timestamp) and stored on the lead record.
4. The response schema rejects any populated `medical_profile` without affirmed, versioned medical consent.

## 4. Scripting (compliant replacements)

- **Pre-frame (exact):** "Just because you might have medical conditions or take medications, doesn't mean you are disqualified from life insurance. By answering these questions, it allows me to focus on what carriers best suit your current profile."
- **Transparency (neutral fact):** carriers may review an MIB report and attending physician statements when an application is submitted; withholding accurate information can hurt the user's own application. Stated as fact, never as a threat.
- **Diabetes (alternative choice, one question per turn):** "Are you controlling that with daily pills, or are you taking insulin?" → "Are you Type 1 or Type 2? And what was your most recent A1C reading?"
- **Cancer:** "What type of cancer were you diagnosed with, and how long have you been completely cancer-free?"
- **Objection deflection with purpose:** "Carriers evaluate diabetes and cancer history differently based on type, treatment, and time. Your best estimate lets the licensed broker match carriers." — then continue; never argue or repeat.
- **Refusal:** accept once, do not re-ask the same declined field, return to education or licensed-broker handoff.

## 5. Explicitly NOT implemented (prohibited)

- "Go ahead with that" as an assumptive consent/close.
- DOT "takeaway" threats ("we can just stop right now, because the carriers will decline the application anyway").
- "The better the price I can get you" / any promise of price, approval, or outcome.
- Claiming to be the user's attorney, doctor, or advisor.
- Any guilt, fear, scarcity, shame, or repeated persuasion (system prompt §7, `PROHIBITED_PRESSURE_TACTICS`).
