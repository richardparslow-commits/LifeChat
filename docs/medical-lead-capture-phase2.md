# Medical Lead Capture — Phase 2 (Compliant Design)

**Status:** Draft — **requires Texas insurance counsel and compliance approval before any use.**
**Scope:** Consented medical fact-finding so Richard Parslow (licensed Texas life-insurance broker) can focus on carriers that fit a user's profile.
**Relationship to the request:** The original request contained scripts using prohibited pressure tactics (assumptive closes, scarcity/takeaway, fabricated decline claims). This document implements the same business goal in a compliance-safe form. The pressure tactics are intentionally **not** implemented and are listed in §5 as prohibited.

---

## 1. When this flow runs

- **Phase 2 only**, gated behind the medical capture feature flag and `healthDataCollectionDisabled=false`.
- **Only after** the user opts into the optional medical review.
- **Only with** explicit, current, versioned medical consent (`medical_consent_affirmed=true` + a current `medical_consent_version`).
- Never in the default educational flow (system prompt §7 forbids these fields without consent).

## 2.1 Canonical condition crosswalk (implemented)

Stated conditions arrive as free text ("sugar diabetes", "high BP"), which cannot be matched or queried. `src/medical/condition-crosswalk.ts` maps them onto a small, versioned vocabulary — one ICD-10-CM code, canonical name, and body system per condition — so a profile is grouped the same way every time.

Rules the code enforces:

| Rule                        | Behavior                                                                                                                                                                                                                                                                                                                                                                                                      |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Consent gate first          | `mapConsentedMedicalConditions()` (capture) and `screenConsentedConditions()` (query) are the only production entry points, and both return `null` unless the flow is enabled **and** medical consent is affirmed **and** versioned — through one shared `isMedicalProcessingPermitted()` helper, so the two cannot drift. Neither is a side door around `HEALTH_DATA_COLLECTION_DISABLED` or the chat gates. |
| Never guess                 | Matching is exact against a curated alias index after light normalization. No fuzzy/substring matching, no inferred codes. Unmatched text is returned in `unmapped` and left in the user's own words — "complete" means every condition is matched or explicitly flagged.                                                                                                                                     |
| Additive, not destructive   | `medical_conditions` stays verbatim on the record; canonical refs are stored **alongside** it as `canonical_conditions`, tagged with the vocabulary id + version so a later mapping change is reproducible for counsel.                                                                                                                                                                                       |
| Clinical normalization only | A ref classifies what the user reported. It is never an underwriting judgment, eligibility finding, or carrier decision, and is never shown to the user.                                                                                                                                                                                                                                                      |
| Sensitive by classification | Canonical refs are TDPSA sensitive health data: encrypted operational record only — never analytics, session history, logs, or the chat response.                                                                                                                                                                                                                                                             |

Vocabulary id `lifechat-condition-v1`, current version **`1.17.0`**, covers the domains the approved topics and the review literature exercise — cardiovascular (including acute events, arrhythmia, and venous thromboembolism), metabolic/endocrine, autoimmune/inflammatory, neurodegenerative, neurological (including transient ischemic attack, neuropathy, traumatic brain injury), respiratory, sleep, renal, musculoskeletal, gastrointestinal/hepatic, mental health, oncologic (the major tumor sites), hematologic, and infectious — plus the common-chronic domains outside the literature sweep that a carrier medical-history questionnaire still enumerates: gynecologic/reproductive, urologic, dermatologic, ophthalmologic/otologic, ENT/oral, congenital/developmental, and the residual musculoskeletal, gastrointestinal, hematologic, infectious, oncologic, endocrine, respiratory, and mental-health rows — plus, since `1.12.0`, the **history and status rows** a carrier questionnaire asks by name: family history of the conditions it screens for, personal history of infection, cancer and circulatory events, genetic carrier and susceptibility status (cystic fibrosis carrier, BRCA), asymptomatic HIV status, do-not-resuscitate status and drug allergy, each mapped to its own _history_ code rather than to the disease's code — and, since `1.13.0`, the two families that chapter had left gated without a code: the **maltreatment histories**, split by setting (physical and sexual, psychological and neglect, each in childhood or adulthood: Z62.810–Z62.819, Z91.410–Z91.419) and the **self-harm pair**, split by intent (suicidal behaviour Z91.51 and nonsuicidal self-harm Z91.52). Both are split by something the person's own words carry, so the row is chosen by what the statement names; the wording that names neither setting nor intent (“history of abuse”, “history of self-harm”) stays unmapped on purpose, because every member's title requires the distinction and the codebook routes the bare phrase to a non-billable header. Since `1.14.0` that family is **complete**: the named kinds the `1.13.0` rows left to their unspecified members are canonical rows — childhood forced labour or sexual exploitation (Z62.813), child financial abuse (Z62.814), childhood intimate-partner abuse (Z62.815), adult financial abuse (Z91.413), adult intimate-partner abuse (Z91.414) and forced labour or sexual exploitation (Z91.42) — and the codebook decided each pair's shape rather than the family being made uniform: the financial and intimate-partner pairs are setting-qualified in both titles and share their generic wording with disjoint markers (the `1.13.0` machinery), while the forced-labour pair is the one asymmetry, because Z91.42's title carries no setting word at all and the index routes “forced labour” to it, so only the childhood row's wording names the setting. A test locks the vocabulary to be unambiguous (no alias claimed by two codes unless a declared qualifier makes the claims disjoint, unique ICD-10-CM codes) so an ambiguous entry fails the build instead of resolving silently. Since `1.15.0` a British/American spelling difference is **declared once** rather than duplicated per alias: `SPELLING_VARIANT_GROUPS` names the interchangeable spellings of a word, and the resolver claims every alias in every declared spelling of it (word by word, the plural carried across), so `['anemia', 'anaemia']` and the forty other duplicated pairs are gone from the data while the spelling is still reached wherever the word occurs — the declaration replaces duplication instead of curating the same diagnosis twice. Since `1.16.0` the vocabulary also covers the **mental and behavioural disorders a person states about their mind**, which the ICD-10 Chapter V enumeration (F00–F99) measured it looking straight through: manic episode (F30.9), paraphilia (F65.9), the severity rows of the intellectual-disability block (mild F70, moderate F71, severe F72, profound F73, unspecified F79, with the generic wording on the unspecified member), and “depressive episode” as an alias on the F32.9 row it already carried. Since `1.17.0` it also covers the **peripheral-nerve and muscle rows the physical-condition sources never surfaced**, which the ICD-10 Chapter VI enumeration (G00–G99) measured silent: spinal muscular atrophy (G12.9), dystonia (G24.9), hemiplegia (G81.90), primary disorder of muscle (G71.9), myopathy (G72.9), trigeminal neuralgia (G50.0), toxic encephalopathy (G92.9), disorder of brain (G93.9), disease of spinal cord (G95.9) and the nervous-system residual (G98), each row also carrying its codebook category-title alias so the sweep's own wording resolves.

**Some codes depend on what the person said about themselves, not on more clinical detail.** Since `1.10.0` a row may declare an `appliesWhen` qualifier — a **sex** or a **site** — and the resolver uses it instead of leaving the condition unmapped. Sex comes from the consented profile's `gender` field and only when it is explicitly `male` or `female`; `other`, `prefer_not_to_say` and an unanswered field are all treated as unknown, and a sex word inside a stated condition is never parsed out of prose. A site is matched in the person's own words (`bladder calculus`, `lump in my breast`), including the spelled-out codebook forms, which resolve by stripping the declared site word and matching the remainder — the qualifying rule the stone-family residue asked for. A qualifier only ever chooses between siblings that were already curated: it never widens a match, and a phrase that supplies no qualifier resolves to **nothing at all**, which is the never-guess rule expressed as data rather than as an absence. Since `1.13.0` a row may also declare a third kind of qualifier: a **marker** (`words`) — a value the phrase has to name, matched the same way a site is and stripped the same way too, so `history of abuse as a child` reaches the wording both abuse rows claim (`history of abuse`) and only Z62.819 can take it, while the wording with no marker resolves to neither. Two rows may share an alias only when their qualifiers are **provably disjoint**, so the shared phrase cannot be decided by whichever row is read first. Since `1.14.0` the mechanism also has a completed example of **retiring a witness**: Z91.419's `intimate partner` marker existed only because no intimate-partner row did, and it moved to Z91.414 with the wording it witnessed — left in place it would have let the old row keep claiming the phrase the new pair owns.

**The distinctions the vocabulary makes are queryable, and gated the same way.** The qualifier families mean a captured history can carry something a bare code list does not name: the _setting_ of an abuse, neglect or exploitation history (childhood or adulthood), the _intent_ of a self-harm history (suicidal or nonsuicidal), and the organ or sex split a qualified row resolved on. `src/medical/condition-screening.ts` names each of those as a declared **screen axis** — an id, the question in words, and its values with the ICD-10-CM codes whose codebook titles express them (`abuse_setting`, `self_harm_intent`, `resolved_site`, `resolved_sex`). An underwriter screens a consented profile's captured `canonical_conditions` by asking one or more filters (`{ axis: 'abuse_setting', values: ['childhood'] }`) and receives the refs that answer, each with the vocabulary version it was mapped under; each filter is asked in full independently, so a conjunctive screen ("childhood abuse **and** a suicidal history") is read from `answers` / `all_answered` rather than collapsed into one yes. Three properties keep it honest. It is **declared, not inferred**: a test proves every member code's codebook title carries its value's signal, that a signal never matches a sibling value's members (the sleep-apnea title `(adult) (pediatric)` is an age range, not an abuse setting, and is asserted to be off the axis), that every marker-bearing row sits on a marker axis in the right value, and that the maltreatment family is exactly its two setting values plus the declared `unstated` member — so a future release cannot add or move a sibling row without the axis recording the decision. It is **honest about what is not distinguished**: Z91.42 ("personal history of forced labor or sexual exploitation") carries no setting word, so screening `childhood` or `adult` never matches it, while asking the axis without a value returns it as `unstated` — "the code does not say" is an answer, and a silent omission would read as "no history here". And it is **gated**: `screenConsentedConditions()` clears the same gate the capture path does, reads only the stored refs (never the verbatim `medical_conditions`), refuses a misspelled axis or value id loudly instead of answering "no", and matches by code, so a record mapped under an older vocabulary version screens the same way. A screen reports what was captured; it is not an underwriting finding, an eligibility decision, a rating, or a carrier rule. No vocabulary version changed: the axes add no codes, names, systems or aliases — they name distinctions the coded rows already carry.

**Any** change to a code, canonical name, body system, **or alias** is a version bump with a `CONDITION_VOCABULARY_CHANGELOG` entry in `src/medical/condition-crosswalk.ts`. That array is the source of truth for the table below and for the added codes, and it is asserted directly by the test suite. An alias move is recorded with the same weight as a code change, because a record mapped under the older version resolved the same stated text to a different code — the entry is what makes that record explainable later.

Three tests keep this table honest: every added code must exist in the vocabulary, every moved alias must actually resolve to its new code and no longer to the old one, and each release's condition count must equal the previous count plus what it added — so the vocabulary cannot be edited without recording the release.

**Coverage is a two-way invariant, not a size target.** The vocabulary is "complete" in the only sense that survives review: every canonical alias is classified as health data by the gate (or is a documented `GATE_EXCLUDED_TERMS` entry), **and** every term the gate watches for either resolves to a canonical entry or appears on the documented list of descriptive terms (body systems, measurements, symptoms, pathoanatomic categories) that are not reportable conditions. Adding a condition term to the gate without a crosswalk entry fails the build, and vice versa — so "what is still unmapped" is answerable from the test output rather than from memory.

**"Complete" is declared, not implied.** Since 1.2.0 the claim has a named scope rather than an open-ended promise: `CAPTURE_SCOPE` in `tests/medical-condition-gate.test.ts` lists the common chronic conditions a carrier medical-history questionnaire enumerates, grouped by domain, each paired with the code it must resolve to. Each declared scope is asserted as behaviour in both directions — every phrase must reach exactly its declared code and classify as health data, and each scope's code list must equal its release's changelog entry, so the declared scopes, the release notes, and the live vocabulary cannot drift apart. Everything in the vocabulary that is _not_ in the scope must be source-derived (1.0.0/1.1.0), and every scope code must exist in the vocabulary.

Deliberately outside the **vocabulary**, with reasons: acute and self-limited infections (urinary tract infection, mononucleosis), injuries and fractures, symptom phrases (brain fog, fatigue), procedure states (hysterectomy), functional and cover-definition rows (blindness, loss of speech, terminal illness), and anything whose code would have to be guessed — the carrier covered-condition lists (1.6.0) are made almost entirely of those rows. Since 1.4.0 those same rows are still **gated** — a disclosure of them is classified as health data — but they carry no canonical code, because the vocabulary's contract is diagnosed conditions and inventing a code the person did not state would break the "never guess" rule. Out-of-scope text is never coerced — it is returned in `unmapped` in the person's own words, which is what makes the boundary reviewable rather than invisible.

**The residual gap is measured, not asserted (1.3.0).** A second declared scope, `RESIDUAL_SCOPE`, records the rows two boundary probes found were **neither gated nor mapped** — a disclosure of those travelled to the model untouched and could not be matched afterwards. It is enforced by the same ledger as `CAPTURE_SCOPE` (each phrase resolves to its declared code and is gated; each scope equals its release's `added` list; nothing in the vocabulary sits outside a declared scope unless source-derived). The probe terms themselves are kept verbatim in `BOUNDARY_PROBE_TERMS`, with an assertion that **nothing a probe surfaced is left ungated**: a row may be gated without a code (acute infections, injuries, symptoms, dental and cosmetic findings — each listed on `DESCRIPTIVE_GATE_TERMS` with its reason), but silence is not an allowed outcome. Latest measurement: 64 probe rows, 40 mapped and gated, 24 gated-but-uncoded by policy, 0 silent pass-throughs.

**The third gap is measured the same way (1.4.0).** `PROBE_GAP_SCOPE` records the named diagnoses a 237-phrase carrier-questionnaire sweep (2026-09-19) found were **neither gated nor mapped**, added in six batches of five; the sweep's procedure states, acute infections, and symptoms became documented descriptive gate terms instead of invented codes. `BOUNDARY_PROBE_TERMS` carries the sweep's rows verbatim, with the same closure assertion. Latest measurement: **237 candidates, 55 neither gated nor mapped, all 55 closed** — 28 became new canonical conditions (among 30 codes added), 3 became aliases on existing rows, and 24 became descriptive gate terms (procedure states, acute infections, symptoms, and HPV). The last row, `piles`, closed in **1.5.0** rather than by deferral: it is now an alias on the hemorrhoids entry (K64.9) and is gated by a context rule, because its collision is syntactic — the ordinary sense is the quantifier and phrasal-verb shape ("piles of paperwork", "the work piles up", "he piles on the pressure"), which the rule excludes with a negative lookahead, while a disclosure ("I have piles"), a clinical qualifier ("bleeding piles"), or a possessive ("my piles") supplies the medical reading. The boundary ledger has no deferred rows left, and a test asserts that.

**The phenome cross-check covers the batch it was built for (1.4.0).** The vocabulary additions since — including the 1.13.0 maltreatment and self-harm rows, which are risk-factor _histories_ rather than outcomes a sequela map could grade — are recorded against their own sources (the codebook enumerations and the scopes above) instead. The vocabulary and the PTSD phenome map (`src/phenome/ptsd-phenome-map.json`, built from the three reviewed syntheses under `docs/phenome-mapping-rules.md`) answer different questions, and `src/phenome/sequelae-crosswalk.ts` keeps them from being read as each other: each condition added to `lifechat-condition-v1` is marked `graded_row` (the map carries a row, and the entry repeats that row's tier), `d_no_studies` (a plausible sequela no source measured — R43's explicit finding, never "no association"), or `not_a_sequela` (present at birth, chromosomal, or hereditary with childhood onset). The cross-check of the 30 conditions **1.4.0** added is deliberately unflattering: **one** (paroxysmal supraventricular tachycardia) is covered by any row, and that row is tier `D` — mechanism-only — because reduced heart-rate variability is asserted with no epidemiology. Twenty-three are study gaps; six are exclusions; and nine could not be placed in a domain at all, because the phenome map's §12 sweep has no dermatologic, lymphatic, urologic/genital, ophthalmologic, or congenital domain — a gap the crosswalk records in words rather than hiding. Forcing that cross-check is what surfaced the map's own missing domain rows: renal, neurological, respiratory, gastrointestinal/hepatobiliary, and oncologic outcomes had no row, so they were added as explicit `D` rows, alongside the two rows the reviewed literature already supported (severe infection at tier B, and the mandatory `trauma`-stratum functional-somatic row).

**The fourth gap was found by a different _kind_ of source (1.6.0).** The three sweeps above all measured the same register — what a person, or a questionnaire, says about their history. A carrier's critical-illness covered-condition lists are different: they enumerate what a _claim_ is triggered by, so they name the catastrophic end of the spectrum an underwriter asks about (coma, paralysis, organ transplant, terminal illness, loss of sight or speech) and the conditions a payout hinges on. `CRITICAL_ILLNESS_SCOPE` records the ten named diagnoses a 51-phrase sweep of those lists found were **neither gated nor mapped**, added in two batches of five. The rows the lists also carry that are not diagnoses — procedures (bypass, valve surgery, transplant), injuries (burns, head trauma), and functional or cover-definition rows (blindness, loss of sight, loss of speech, paralysis, terminal illness, loss of independent existence) — became documented descriptive gate terms instead, which is why the corpus measures 23 mapped-and-gated and 28 gated-but-uncoded, with **0 silent**. Three aliases landed on existing rows rather than new codes: the two spellings of pulmonary hypertension, and `loss of hearing`, which the vocabulary already carried as hearing loss (H91.90) — the list simply named the same condition differently (and, since the questionnaire corpus spells it the same way, it moved that corpus's single row too: 184 mapped-and-gated, 53 descriptive).

**The fifth gap came from a code book (1.7.0).** Every source so far had been prose a human wrote _about_ a person — a questionnaire, a covered-condition list. The next one is a classification structure: the three-character category titles of WHO ICD-10 Chapter IX, 77 rows written to organize codes rather than to describe anyone. Measuring it asked a harder question than the earlier sweeps did — not "does the gate see this sentence?" but "when a person states the thing the code book names, does either system see it?" — and the answer found three kinds of hole. Two were spelling: the vocabulary carried `hemorrhage` and `hemorrhoids` but not the British `haemorrhage`/`haemorrhoids`, so a British visitor's haemorrhagic stroke and haemorrhoids were both **silent**. One was a synonym: `stroke` was mapped, `cerebral infarction` was not. Three were conditions nobody had named yet (phlebitis, nonspecific lymphadenitis, atrioventricular block). The remaining category constructs — "other diseases of pericardium", "other disorders of arteries and arterioles", "other disorders of veins", "diseases of capillaries", "other and unspecified disorders of circulatory system" — are not diagnoses anyone states, so they are now gated by a narrow clinical term (`pericardium`, `arteriole`, `veins`, `capillaries`, `circulatory`) rather than given an invented code. One of those terms carries a stated cost: `veins` is word-matched in the plural only, so "in the same vein" stays clear while the metaphor "the veins of the market" is gated — the fail-safe direction, recorded rather than hidden.

**The sixth measurement came from the same code book, one chapter across (1.9.0).** The Chapter IX sweep asked whether the vocabulary sees what a code book names; the obvious next source was the chapter the stone family itself sits in — N00–N99, diseases of the genitourinary system — whose 85 category titles are almost all _constructs_ rather than diagnoses ("other disorders of bladder", "other noninflammatory disorders of the vagina"). That is why this sweep's shape is different from every earlier one: 41 rows were silent, but only thirty of them name a diagnosis a person could state. Those thirty are canonical rows in six batches of five, each title verified against ICD-10-CM before use. The constructs close as documented descriptive gate terms, and the sweep found two genuine codebook holes worth recording: `urethral stricture` has no sex-free billable code since FY2026 split N35.9 into N35.91 (male) and N35.92 (female), and the corpus row `benign mammary dysplasia` needed the site-free member N60.99 rather than the N60.9 header, the same way `unspecified lump in breast` needed N63.0 — the lump rule's own row, finally matchable. One alias moved: an unqualified `kidney failure` is the unspecified row (N19), not end-stage renal disease. The corpus therefore measures **85 candidates, 28 mapped and gated, 57 gated-but-uncoded by policy, 0 silent** — the largest gated-not-coded share of any source, which is the honest signature of a classification structure rather than a description of a person.

**The hole the code book left became a design change (1.10.0).** The Chapter XIV sweep ended with one row it could not code honestly: `urethral stricture`, because FY2026 had split N35.9 into sex-specific codes and any single choice would have been a guess about the visitor. That is a resolver gap, not a coverage gap, and the fix is the one the 1.8.0 residue had already asked for in different words: let a row declare its dependence instead of being unrepresentable. So `appliesWhen` was added — a sex qualifier read from the consented profile (never from prose, and never inferred from `other` or an unanswered field), and a site qualifier read from the person's own words, with the spelled-out forms resolving by stripping the declared site word and matching what is left. The same mechanism closed a second residue: the generic `calculus`/`calculi` spellings now reach the kidney, ureter and bladder rows exactly when the organ is named, and a bare `calculus` resolves to nothing, which is why `calculus` and `calculi` sit on the documented gate-exclusion list with their mathematics-sense reason. Two rows were added (305 codes), the release declares a qualifier-aware scope whose groups carry the sex each phrase must be asked with, and — the gap this work exposed in its own test suite — the scope list is now compared against the changelog rather than against itself, so a future release cannot add codes without declaring a scope.

**The seventh measurement is the chapter where the code book stops describing people (1.11.0).** Chapter IX and XIV are lists of diseases; Chapter XVIII — R00–R99, symptoms, signs and abnormal clinical and laboratory findings — is a list of _what a clinician observes_, and 55 of its 86 category titles were **silent** against both systems: not because the vocabulary was thin but because most of the chapter is not a diagnosis at all. That forced the release into two different closures rather than one. The rows that do name a discrete finding with a billable member — a nosebleed, a fainting episode, a swollen gland, a marker that came back high — became canonical rows in the batches above, each title verified against ICD-10-CM FY2026 first, with two categories where the header is non-billable resolving to their "other" member instead. Everything else — the symptom nouns (`cough`, `nausea`, `headache`), the report headings (`abnormal results of function studies`, `abnormal findings on diagnostic imaging of…`), the clinical category words (`debility`, `cachexia`, `hyperhidrosis`) and the shock row's own adjectives — closed as **documented descriptive gate terms**: the disclosure is protected, and the vocabulary does not invent a diagnosis the person did not state. Three R00–R99 rows cannot be a disclosure in this product's conversations at all (R27 "other lack of coordination", R57 "shock, not elsewhere classified", whose bare noun is the product's own vocabulary, and R99 "ill-defined and unknown cause of mortality", a death-certificate construct), and those are **declared in the corpus file itself with a reason** rather than listed as candidates — a declaration a later sweep re-reads rather than a gap it re-discovers. Two words needed the context-qualified registry instead of a bare token, because their ordinary senses are common and measurable: `rash` ("a rash decision") and `pain` ("the pain points", "a pain in the neck"), each now carrying a two-directional corpus. The chapter also produced the release's one honest-codebook note: `numbness` and `tingling` are gated but uncoded, because the code book splits the complaint between R20.1 (hypoesthesia) and R20.2 (paresthesia of skin, which the release carries) and the message does not say which.

**The eighth measurement is the chapter that is not about diseases at all (1.12.0).** Chapter IX, XIV and XVIII are enumerations of _conditions_; Chapter XXI — Z00–Z99, factors influencing health status and contact with health services — is an enumeration of _statuses, encounters and history_, and it is where a carrier's questionnaire actually lives: “has anyone in your family ever had…?”, “have you ever been treated for…?”, “are you allergic to anything?”. Measuring it asked a question no earlier sweep had asked — not “can the gate see this disease?” but “is a _statement about a person_ seen at all?” — and the answer was the largest gap of any source: **61 of 90 titles silent**. **Re-running the measurement (the sweep tool).** The numbers above come from a measurement, so the measurement is a committed tool: `npm run conditions:sweep` runs a candidate list through both systems and reports every row as mapped-and-gated, mapped-but-ungated, gated-but-uncoded, classified-otherwise, **silent** — the class the sweeps exist to find — or **deferred**, a row the project deliberately left open with its reason on file. It exits non-zero on silent or mapped-but-ungated rows, so a corpus can gate CI the way the verdict and persona gates do; a deferral does not fail the build while its row is still silent, and one whose row is no longer silent **does**, because then the ledger is stale. **Six** corpora are committed and swept by default: `docs/medical-condition-candidate-phrases.txt` (the 237 phrases the questionnaire sweep was measured against), `docs/medical-condition-candidates-critical-illness.txt` (the 51 phrases the carrier covered-condition lists yielded), `docs/medical-condition-candidates-icd10-chapter-ix.txt` (the 77 three-character category titles of ICD-10 Chapter IX), `docs/medical-condition-candidates-icd10-chapter-xiv.txt` (the 85 category titles of ICD-10-CM Chapter XIV, the chapter the stone family sits in), `docs/medical-condition-candidates-icd10-chapter-xviii.txt` (the 86 category titles of Chapter XVIII — symptoms, signs and laboratory findings, the chapter that is mostly not a diagnosis) and `docs/medical-condition-candidates-icd10-chapter-xxi.txt` (Chapter XXI's 90 titles, of which 41 are candidates — the other 48 are declared non-stateable in the file, with reasons) — all written down before any of their rows were mapped. Alongside them, re-asked on every run, is `docs/medical-condition-deferred-candidates.txt` — not a source of new phrases but the **deferral ledger**: the rows a sweep surfaced and the project deliberately left open, each written as `? <phrase> :: <reason>` (a JSON list may carry `{ "phrase", "deferred_reason" }` objects instead). The reason is required rather than optional, and a phrase cannot sit on the ledger and in a corpus at once. Every run measures each ledger row afresh — a declaration is not a stored verdict — and reports it as `deferred` with its reason rather than as a gap; the moment one stops being silent the entry is **stale** and blocks until the ledger is updated, so a deferral can neither be dropped nor quietly become a closure. `rash` is the worked example of a deferral that ended: deferred by the lay-word measurement, closed by the Chapter XVIII release, and gone from the ledger. ```bash

npm run conditions:sweep -- --all               # every row, not only the problems
npm run conditions:sweep -- my-questionnaire.txt
npm run conditions:sweep -- --json

**"Condition" is only a health word in context.** The disclosure list watched the bare word, so it matched any sentence containing it — "what conditions apply to my application?", "what are the terms and conditions?", "conditions of sale apply", "market conditions are rough" were all classified as health data and handed off. Deliberately not counted, each because it is idiomatic in the contractual sense: `any` ("are there any conditions on the payout?"), `other` ("other conditions apply"), and the bare plural. First-person plurals with no qualifier ("I have other conditions", "I have conditions that are managed") are covered by a separate clause, because a bare plural would otherwise fall through and that is a real disclosure phrasing — requirements attached to a product are not something a person _has_ about themselves. **The rest of the meta words, same treatment ("treatment", "heart", "symptom", "prescription", "disease", "disorder").** Each also matched bare, and each collides somewhere in this domain: `treatment` ("what is the tax treatment of the proceeds?", "the treatment of the claim", "equal treatment for all applicants"), `heart` ("at the heart of the matter", "the heart of the policy"), `symptom` ("a symptom of a slow claims process"), `prescription` ("the prescription of rates"), `disease` ("the disease of rising premiums"), `disorder` ("the disorder of the ledger"). The negative rule exists because the first version — positive qualification, the same shape as `condition` — silently dropped named conditions: `peripheral artery disease`, `reactive airway disease`, `chronic obstructive pulmonary disease`, `post-traumatic stress disorder` and `panic disorder` all stopped being classified as health data, because nothing in those names is a "qualifier" the rule could have listed. Two medical "of" shapes are opt-in exceptions ("symptoms of my condition", "a disease of the liver"), and `heart` deliberately does not take them, because for `heart` that shape _is_ the metaphor ("the heart of my plan"). `heartburn` is its own entry: it is the vocabulary's synonym for GERD, and `\bheart\b` never matched it.

**The seven are one registry now, not seven regex families.** `src/security/context-family-terms.ts` declares each word as a single object — its spellings, its rule shape, and the ordinary sense written down — and every pattern is generated from that data, the same move `context-qualified-terms.ts` made for the excluded tokens. A `context-required` entry lists its clauses in the order they were measured (`owner`, `disclosure`, `possessor`, `definite-article`, `qualifier`, `anchor`, `verb`, `example`), each carrying the words or introducers it counts; an `of-metaphor-excluded` entry declares `medicalOf` explicitly, which is why `heart` cannot inherit the medical "of" clauses the other four take. What used to exist only as an inline regex is now data a test can read: `condition`'s singular-only `the` clause names the spelling it watches, `treatment`'s owner clause carries `excludeOf: true` inside the generated pattern — so a clause cannot be added without the lookahead that makes "the treatment of the claim" ordinary — and `heartburn` is listed with the reason it belongs to the heart family. `tests/context-family-terms.test.ts` asserts the structure (every pattern watches the spellings it was declared for, each rule carries only the data it reads, a definite-article clause may only name a declared spelling) and proves the machinery is data-driven with synthetic entries run through the production builder. | `drink`   | all silent already                                                                                                   | "I drink two units a week", "how much do you drink?", "I stopped drinking", "I don't drink", "I have a drinking problem", "my drinking habits changed"                                | coverage rule — quantity, practice verb or habit noun; "do you drink coffee?" is carved out              |

The `illness` carve-out is a lookahead rather than a lookbehind, and that is the whole design: "**I have a critical illness**" is a disclosure and "does it include **critical illness cover**" is not, so only the following word distinguishes them. The list is the sales nouns — cover, insurance, policy, plan, quote. `claim` was tested and deliberately left _in_: "my critical illness claim was refused" and "I filed an illness claim" are statements that imply the condition, and the general question form ("how does a critical illness claim work?") comes out a health **topic** question, which is the right classification for it anyway. Bare "is illness covered?" is likewise a topic question, not a disclosure.

The adjective `ill` needed one extra care that only showed up in testing: a hyphen is a word boundary, so the copula form swallowed "is **ill**-advised" and "am **ill**-prepared". Every `ill` pattern now carries a `(?!-)` lookahead — the hyphen _follows_ the word, so a lookbehind would never see it — and both collisions are asserted as benign.

Two limits are worth stating rather than implying: "I am stressed" and "I feel stressed" are left ungated, because in this domain they are colloquial and the clinical forms (levels, leave, a clinician, a consequence) are what a disclosure looks like; and "I smell smoke" is not caught, since the pattern requires a person as the _subject_ of smoking rather than someone near it.

Each of the twenty words now carries **both** corpora in `tests/gate-road-test.test.ts` — a benign list proving the ordinary sense stays silent and a medical list proving the narrowing cost no real disclosure — plus a structural assertion that no word can be narrowed without both. Writing them caught a silent coverage loss of its own: the first `prescription` pattern was singular, so "my prescriptions are expensive" matched nothing.

**How the endpoint half of the suite is kept honest.** One full-suite run failed a single endpoint assertion — an ordinary sentence classified as a handoff — and passed in every rerun, so the first job was to make that kind of failure diagnosable and its causes impossible rather than to declare it fixed. Four changes:

- **A fresh app per endpoint test.** The `/api/chat` describes used to share one app instance per describe, which means one rate-limit store, one session store, one page-context bridge and one module registry across ~40 requests. Nothing in the gate reads those, but an endpoint test whose outcome depends on how many requests ran before it cannot be trusted to fail for its own reason. `loadApp()` resets the module registry, so `beforeEach` now builds an app whose module state is pristine, and every test does one request against it.
- **One object comparison instead of one field at a time.** The failing test was asserted field by field, so the only evidence a rare failure leaves is a single field name. It now compares `{status, state, risk_flags, assistant_message}` in one `toEqual`, so a recurrence prints the whole response.
- **The violated property, asserted directly.** Classification must be a pure function of the text: the same sentence is classified 200 times in a row and must return the same category every time (the stateful-regex and module-counter class of bug), and the same benign message is sent twelve times through the endpoint — eleven fresh sessions plus one repeat — and must come back identical and never a handoff.
- **Cross-instance agreement.** `loadApp()` resets the module registry, so the app runs a _newer_ instance of the security module than the one the test file imported at the top. The two are now asserted to agree on a sample, because if they ever drifted, every unit assertion in the file would be describing a gate the endpoint does not run.

Stability is then measured, not asserted: six consecutive full-suite runs, a serial run (`--maxWorkers=1`), a high-parallelism run (14 workers) and a deliberately tight per-test timeout (`--testTimeout=400`, against a 5-second default and measured per-test times under 400 ms) all pass 1349 tests. **A later measurement pass recovered the failure's signature, which is worth recording because it is not the class this work hunted.** The symptom is a response of **405**, and it lands on _unrelated_ routes and methods in _different_ suites — a `GET /api/disclosure` one run, a `GET /api/session/:id/history` another, a `POST /api/dsr` a third — which rules out any single endpoint's logic. It is also **not** Express's method-mismatch behaviour: measured against the installed Express (4.22.2), a method mismatch on a matched path answers **404** and sets no `Allow` header, and there is no literal `405` anywhere in `src/` or `tests/`. It reproduces in roughly one full-suite run in three to five, seen at default parallelism, at `--maxWorkers=2` and once at `--maxWorkers=1`, so it is not purely a parallelism race either. The next hunt should therefore start from the **request and the response** that produced the code — its `Allow` header, its body, and the socket the client connected to, since every `loadApp()` imports `src/index.ts`, which binds an ephemeral port as a side effect, and supertest then opens a real loopback connection — rather than from the assertions. The three rows it has spent (`/api/disclosure contextual behavior`, the contract-question endpoint table, and the untracked `server-hardening` write-budget test) are now attributed rather than re-diagnosed each time. No leaked handles are reported. The observed failure's exact field was never recovered — which is why the assertions now print all of them — and `state: 'handoff'` has exactly two reachable producers, the sensitive-data refusal and the PII-to-state-machine path, neither of which the current patterns can produce for an ordinary sentence.

**A question about a condition is not a disclosure of one.** (Gate change only — the condition vocabulary and its release history are unchanged. No conditions were added, so no changelog entry applies.) Asking "Is TB curable?" handed off the same way as saying "I have MS", and was classed the same way — which misstated the visitor's action: the reply told them not to share diagnoses, the message was redacted as a disclosure, and the record carried `sensitive_data_disclosed`. Whether that happened at all was incidental, depending on whether the vocabulary happened to cover the condition: "What is lupus?" was blocked, "Is TB curable?" and "does MS affect my life insurance rate?" travelled to the model untouched. The classification is now explicit and decided by one rule, `detectHealthTopicQuestion()`: a leading interrogative, a condition reference (crosswalk vocabulary, the common named conditions, or one of the four abbreviations with the guards applied), and **no first-person or family framing**. Three outcomes, not two:

| Input                                                                  | Classification          | Why                                                                                   |
| ---------------------------------------------------------------------- | ----------------------- | ------------------------------------------------------------------------------------- |
| "I have MS", "my SLE is stable", "history of TB"                       | `health_data`           | the visitor's own health                                                              |
| "does MS affect my rate?", "do I have MS?", "does my father have MS?"  | `health_data`           | personal framing makes the question a personal health question — an implied condition |
| "Is TB curable?", "What does TIA stand for?", "How is cancer treated?" | `health_topic_question` | about a topic, about nobody in particular                                             |

The safety property is identical in all three: blocked before the model, deterministic licensed-broker handoff, message kept out of session history so a later turn cannot put the condition in front of the model, and `medical_review` with affirmed consent remains the only surface that accepts it. **The two rows above are the two of those three outcomes the visitor meets; the third has since been split.** An impersonal question about a condition that is framed as a question about the _policy's own wording_ ("does the policy have a cancer exclusion?", "does the suicide exclusion apply after two years?") is a **contract question**, not a health topic: the condition named is the provision's subject, so it is answered as a product question and nothing about the visitor's health is flagged or withheld — the rule, its frame, its guard and its boundaries are in the contract-question paragraph below. What differs is the visitor-facing copy (no "don't share diagnoses" for someone who shared nothing), the `handoff_reason` (`health_topic_question`, not `health_data_disclosed`), and the risk flag (`health_topic_question`) — so the compliance record states what actually happened. A trailing question mark alone is not enough ("history of SLE?" stays a disclosure), and the response schema carries the same invariant as the disclosure flag: the topic flag requires `proposed_action=request_human_handoff` or `none`. The split is asserted at the unit level, through `/api/chat`, and in `tests/gate-road-test.test.ts`, where the topic questions previously recorded as undecided judgment calls are now assertions.

**The gate no longer hand-writes a spelling the declaration already declares.** (Gate change only — the condition vocabulary and its release history are unchanged, still 1.16.0.) The 1.15.0 spelling table had one consumer (the resolver) while the gate kept hand-writing the British side of each pair next to its American sibling — twenty-four duplicated entries, plus the stems (`ischaem`, `hyponatraem`, `hypercalcaem`, `hyperuricaem`, `polycythaem`, `oesophag`) whose British forms were separately hand-written too. Since that spelling-derivation release the gate is the declaration's second consumer: it rewrites each watched word with the resolver's own rules (the exact word, the plural carried across) and derives the British form of a prefixed-compound stem by an equal-trim rule — a stem that is a proper prefix of one spelling derives its sibling trimmed by the same amount (`ischemic` − 3 → `ischaem`), and a group without a common ending, or a stem under four characters, derives nothing rather than guessing. The twenty-four British entries are deleted and the twenty-five derived spellings are exported (`ALL_CONDITION_GATE_TERMS`, `ALL_CONDITION_GATE_WORD_TERMS`) and pinned in the gate suite; the derivation closes one real hole for free — the British adjective `seborrhoe` was unwatched (`seborrhe` cannot substring-match `seborrhoeic`), masked until now by `dermatitis` also being gated. One pair stays hand-written on purpose: `gonorrhoea` is not a canonical condition (gated descriptively as an acute, self-limited infection), and every declared group must be reached by the vocabulary, so declaring it would be dead data. Neutrality is proven, not asserted: a 47-sentence corpus (one disclosure per deleted sibling, the American controls, and the ordinary collision sentences) classifies identically before and after, and the parity ledger now checks every spelling of an alias rather than only the curated wording, so the grandfathered British-spelling exemptions are retired from the descriptive list — a derived spelling is accounted by the same canonical alias its sibling is, and the "no half-pairs" invariant means a term can no longer be added in one spelling while silently missing the other. The word-declared properties carry over unchanged: only declared words are rewritten ("your", "four" and "therapeutic" stay untouched), and the accepted `labour`/`tumour` collision trades are exactly where they were.

## 3. Consent flow (implemented)

1. Assistant proposes the optional medical review after qualification, with a just-in-time notice: which fields, why (carrier matching by the licensed broker), optional nature, withdrawal/deletion route.
2. The application presents `RECOMMENDED_MEDICAL_CONSENT_COPY` as an **explicit, unchecked, opt-in** control. Ambiguous or hedged replies are treated as **not** consented (system prompt §9).
3. Consent is versioned (`medical_consent_version` + timestamp) and stored on the lead record.
4. The response schema rejects any populated `medical_profile` without affirmed, versioned medical consent.

## 4. Scripting (compliant replacements)

- **Pre-frame (exact):** "Just because you might have medical conditions or take medications, doesn't mean you are disqualified from life insurance. By answering these questions, it allows me to focus on what carriers best suit your current profile."
- **Transparency (neutral fact):** carriers may review an MIB report and attending physician statements when an application is submitted; withholding accurate information can hurt the user's own application. Stated as fact, never as a threat.
- **Diabetes (alternative choice, one question per turn):** "Are you controlling that with daily pills, or are you taking insulin?" → "Are you Type 1 or Type 2? And what was your most recent A1C reading?"
- **Cancer:** "What type of cancer were you diagnosed with, and how long have you been completely cancer-free?"
- **Objection deflection with purpose:** "Carriers evaluate diabetes and cancer history differently based on type, treatment, and time. Your best estimate lets the licensed broker match carriers." — then continue; never argue or repeat.
- **Refusal:** accept once, do not re-ask the same declined field, return to education or licensed-broker handoff.

## 5. Explicitly NOT implemented (prohibited)

- "Go ahead with that" as an assumptive consent/close.
- DOT "takeaway" threats ("we can just stop right now, because the carriers will decline the application anyway").
- "The better the price I can get you" / any promise of price, approval, or outcome.
- Claiming to be the user's attorney, doctor, or advisor.
- Any guilt, fear, scarcity, shame, or repeated persuasion (system prompt §7, `PROHIBITED_PRESSURE_TACTICS`).
